# Coconut — Budget Tracking Application

## 1. Purpose

Coconut is a private, offline-first Android budget management application designed around
a monthly spending allowance and a savings reserve.

The application is intended for a single user and models the user's personal financial
system. It is not a general-purpose banking or accounting application.

Optionally, two or more authenticated Coconut users can connect in a Shared Space to
track shared expenses (typically a couple). A Shared Space extends, and never replaces,
each user's personal financial system.

There is no bank integration, advertising, analytics, or any required
internet connection. All financial data is stored locally on the device in a SQLite
database that is the single source of truth.

The application is fully usable offline. An optional, opt-in sync to a user-owned
Supabase project can mirror the local database so it is available on the user's own
multiple devices. Sync is never required to use the application and never replaces the
local database as the source of truth.

---

## 2. Core Financial Model

The application is organized around independent monthly accounting periods.

Each month has:
- A guaranteed monthly allowance.
- Fixed expenses.
- Estimated/variable fixed expenses.
- Flexible spending budgets.
- Actual transactions.
- A calculated total monthly spending.
- A calculated difference between actual spending and the monthly allowance.
- A starting and ending savings-reserve value.

The monthly allowance represents the amount of money reliably available for ordinary
monthly spending. It is not a conventional spending budget and does not impose an
artificial spending limit.

The user's planned spending may therefore be greater than the monthly allowance.
The application shows this clearly rather than treating it as an error.

---

## 3. Savings Reserve

The application maintains a separate savings-reserve balance.

The reserve is not treated as an ordinary spending account and does not contain individual
bank transactions. It represents accumulated money available to compensate for months
where spending exceeds the allowance, as well as accumulated savings from months where
spending is below the allowance.

At the end of each month:

    actual monthly spending - monthly allowance = reserve adjustment

The reserve is reduced when actual spending exceeds the allowance and increased when
actual spending is below the allowance.

The resulting reserve balance carries forward into subsequent months.

Additional transfers from the reserve into the current month's available funds are
supported and tracked separately from ordinary spending, so that transferring money does
not incorrectly appear as an expense.

---

## 4. Fixed Expenses

Users define recurring fixed expenses that automatically belong to each relevant month.

Each fixed expense has:
- Name.
- Expected amount.
- Recurrence/configuration.
- Whether the amount is genuinely fixed or estimated/variable.
- Current month's actual amount where applicable.

Genuinely fixed expenses are automatically accounted for using their defined amount.

Variable fixed expenses have an expected amount used for monthly planning. The expected
amount can be determined manually or derived from historical actual amounts.

Supported estimation strategies:
- Manually specified amount.
- Previous month's actual amount.
- Average of a configurable number of previous months.
- Historical average.

When the actual bill becomes known, the user replaces/corrects the month's expected
amount with the actual amount without creating a second expense.

The application retains the distinction between expected and actual values so that
historical statistics and future estimates use actual spending.

---

## 5. Flexible Spending Budgets

Users define discretionary spending categories with monthly budget amounts.

Budgets represent intended spending allocations, not hard restrictions.

The sum of flexible budgets and fixed expenses may exceed the monthly allowance. This is
intentional and supported naturally.

For each budget:
- Planned amount.
- Actual amount spent.
- Remaining amount.
- Difference between planned and actual spending.

Budgets are independently configurable and support being changed for individual months
without unnecessarily changing historical months.

---

## 6. Transactions

Actual discretionary spending is recorded as individual transactions.

A transaction contains:
- Unique identifier.
- Date.
- Amount.
- Category/budget.
- Merchant or description.
- Optional note.

Transactions are manually entered by the user.

Transactions may also originate from a shared expense: each participant gets exactly one
linked personal transaction whose amount equals that participant's split. Linked
transactions are derived from the shared expense and are never edited as a separate
record.

Entering a transaction assigned to a budget immediately updates the relevant budget's
actual spending and the month's overall actual spending.

Transaction entry is extremely fast and simple — this is a frequent operation.

The system remembers previous merchant/category associations locally and suggests
categories during future transaction entry. Suggestions remain editable and do not
prevent choosing another category.

---

## 7. Monthly Accounting

Each month distinguishes clearly between:
- Allowance.
- Planned spending.
- Actual spending.
- Remaining allowance.
- Expected month-end spending.
- Expected reserve adjustment.
- Final reserve adjustment once the month is closed.

The current month is the primary focus of the application.

Previous months remain accessible for review and statistics but do not clutter the normal
current-month interface.

Months are independently preserved so that modifying a current configuration does not
unexpectedly rewrite historical financial records.

---

## 8. Forecasting

The application distinguishes actual financial results from planning/forecasting.

Visible information:
- How much has actually been spent so far.
- How much remains in each budget.
- What fixed expenses are expected.
- What total spending is currently planned or forecast.
- What reserve adjustment is currently expected.

Forecasts are clearly presented as estimates and must not be confused with actual
recorded spending.

- Fixed-expense expectations and actuals.

## 11. Data Storage and Cloud Sync

### 11.1 Local database as source of truth

All reads and writes go to a local SQLite database on the device. The local database is
always the source of truth. The application never loads financial data from the cloud.

The database separates persistent configuration from month-specific financial records.

Capabilities:
- Query current-month data.
- Retrieve historical months.
- Calculate budget totals.
- Calculate monthly totals.
- Calculate historical averages.
- Update variable-expense estimates.
- Recalculate reserve changes deterministically.

Financial calculations are implemented as separate business logic, not embedded in UI
components.

### 11.2 Optional synchronization to Supabase

The user may enable optional synchronization to their own Supabase project so the same
personal dataset is available across their own devices.

- Sync is opt-in. Without it the application is completely local and makes no network
  requests.
- The local database is always written first, then a background, best-effort sync pushes
  the changes to Supabase when the network is available. Sync never blocks normal use and
  never fails local operations.
- Other devices pull those changes into their own local SQLite database; the app on every
  device continues to read and write locally only.
- Sync mirrors row-level changes, not the whole database on every write. Each synced row
  carries a stable UUID and a timestamp and follows last-write-wins conflict resolution.
- The Supabase project is owned by the user and used only for this mirror. No third party,
  tracking, or analytics is involved.

### 11.3 Sync lifecycle

- A write to a local table records the change in a local sync outbox and tombstone log.
- A sync run pushes the recorded upserts and tombstones to Supabase and pulls any changes
  made by the user's other devices.
- Conflicts between devices are resolved by last-write-wins using each row's update
  timestamp.
- Sync state (last push position, last pull time, connection status) is stored locally and
  displayed in Settings.

## 12. Shared Expenses

### 12.1 Concept

Each user keeps an independent Coconut account and personal financial system. A Shared
Space connects two or more authenticated Coconut users (initial use case: a couple
sharing expenses) and holds shared expenses, their splits, and settlements.

The shared-expense relationship is authoritative:

    Shared Expense
      ├── total amount
      ├── payer (a member)
      └── per-participant split
             ├── participant A's personal linked transaction
             └── participant B's personal linked transaction

A participant's personal transaction amount is always derived from their split. Editing a
shared expense re-derives the linked personal transactions; the split is never maintained
independently in two places.

### 12.2 Authentication and security

One Coconut Supabase project hosts all users. There are no per-user Supabase projects,
and users do not share one Supabase Auth account; each Coconut user is a separate
Supabase Auth user.

Supabase Row Level Security distinguishes personal rows from shared rows:

- Personal rows: `user_id = auth.uid()`.
- Shared rows: `auth.uid()` is a member of the relevant Shared Space.

A user cannot read or write another user's personal rows, join a space arbitrarily, or
create expenses/splits/settlements for users outside the space. Every new exposed table
has RLS enabled, and member vs. non-member RLS behavior is tested.

### 12.3 Database model

Adapted with additive, incremental migrations only; existing personal data stays intact.

- `shared_spaces` — name, creator, timestamps, deleted flag.
- `shared_space_members` — space, user, role (`owner`/`member`), joined; unique
  `(space_id, user_id)`.
- `shared_expenses` — space, description, total amount, date, paid by (a member), note,
  creator, timestamps, deleted flag.
- `shared_expense_splits` — expense, user, explicit monetary share in cents. Only
  explicit amounts are persisted; 50/50 and percentage splits are UI conveniences that
  resolve to amounts. Sum of splits equals the total.
- `settlements` — space, from user, to user, amount, date, note, timestamps.

Enforced invariants: totals positive; splits non-negative and summing to the total; payer
and split users are space members; settlement users are space members; no self-settlement.
Validated at data-application and database/business-logic level, never UI-only.

### 12.4 Personal transaction provenance

The existing personal transaction model is extended, not duplicated, with a provenance
reference (`origin_type` / `origin_id`). Manually entered transactions use `manual`; a
transaction created from a shared expense references that expense's UUID. The
transaction's own stable ID remains unchanged.

A shared expense synchronizes to every member's device; each device maintains the linked
personal transaction for that user's own share. When splits change, linked transactions
update in place (never duplicated); when a shared expense is deleted, linked transactions
follow the app's deletion/tombstone model — no orphaned transactions.

### 12.5 Balances and settlements

The net "who owes whom" balance is never stored as mutable state. It is derived from
shared expenses, their splits, and settlements, with a clear sign convention, and reduced
to a single net amount between each pair of members. Coconut shows only the resulting net
settlement.

Settling creates a `settlements` record; it does not modify or delete historical shared
expenses. After settlement the outstanding balance is zero while expense and settlement
history remain visible.

### 12.6 Shared Space lifecycle

- Create: one user creates the space.
- Invite/join: additional users join only through an explicit, secure invitation
  (invitation token/deep link or pending membership). Knowing a space UUID alone grants
  nothing.
- Leave/remove: a member can be removed or leave without deleting historical shared
  expenses.

### 12.7 Sync integration

Shared data (spaces, members, expenses, splits, settlements) uses the same local-first
sync engine as personal data: stable UUIDs, timestamps, outbox/tombstone logs, and the
existing last-write-wins conflict strategy. Multiple members' devices pull the same shared
rows. Splits are validated after synchronization so total != sum of splits is never
silently introduced.

### 12.8 UI

A dedicated Shared area shows spaces, members, the outstanding net balance, settlements,
and the shared-expense list. Adding an expense is fast: description, amount, date, paid by
(me / another member), split method, optional note, and the payer's and each
participant's displayed share. Personal transaction views visibly identify shared-linked
transactions and can navigate to the originating shared expense.

No separate category system: a shared expense may carry an optional category/merchant
association, and the resulting personal transaction uses each participant's own budget
category.

### 12.9 Non-goals

No real-time collaborative editing, no new backend, no second database, no separate
Supabase projects, no dedicated global state for this feature, no bank integration, no
general Splitwise replacement. Use the existing Coconut architecture throughout.

## 13. Backup and Restore

Synchronization and backup are separate features.

- Export complete application data to a portable file (the full SQLite database).
- Import to restore all data.
- Backup includes all information required to reconstruct financial history and
  configuration.
- Backup works entirely on-device; no cloud service is required for it.

---

## 14. Privacy

- Works completely offline.
- Stores financial information locally.
- No network requests during normal, non-synced operation.
- No analytics or tracking. No account in local-only mode; Supabase Auth accounts exist
  only when the user opts into multi-device sync and Shared Expenses.
- No advertising.
- No bank credentials or banking integration.
- Avoids unnecessary permissions.

Financial information leaves the device only when the user explicitly enables
synchronization to their own Supabase project; the app never sends data anywhere else.

## 15. Technical Stack

- React Native (via Expo)
- Expo SDK
- TypeScript (strict mode)
- expo-sqlite (local SQLite database)
- Expo Router (navigation)
- React Native Paper (Material Design 3 UI components)
- dayjs (date handling)
- Jest + jest-expo (unit testing)
- @supabase/supabase-js (optional cloud sync mirror only)
- Expo Web / react-native-web (desktop web builds)

Architecture:
- Business logic, database access, sync, and UI have clear separation.
- Supabase is the only permitted backend: an optional sync mirror for the user's own
  data and the host for Shared Expenses. Supabase Auth identifies users only for these
  optional features; Row Level Security separates personal and shared rows. No other
  backend, provider, or analytics is used.
- Small dependency footprint.
- Favor Expo-supported functionality.
- The application must build and run as a local desktop web application and remain
  structured so a future native desktop app can reuse the same code with minimal work.

---

## 16. Desktop and Web

Coconut targets Android first, but the code must also compile as a desktop web
application that runs locally.

- The web build is a standard Expo Web (react-native-web) single-page build that can be
  served and opened locally.
- expo-sqlite supports web via a WebAssembly SQLite build, so the same database layer and
  the same sync logic run on desktop web without platform-specific forks.
- Native-only capabilities (file sharing, native date pickers) are isolated behind
  platform-safe wrappers so the web build always compiles and degrades gracefully.
- The UI and services layers must stay platform-agnostic. Keeping the database, sync, and
  services layers free of platform bindings is what makes a future desktop app simple: the
  same modules can be packaged with the desktop runtime of choice.

---

## 17. Design Philosophy

Focused personal tool, not a commercial banking application.

Priorities:
1. Extremely clear current-month overview.
2. Fast manual transaction entry.
3. Accurate and predictable calculations.
4. Simple handling of recurring and variable fixed expenses.
5. Clear separation between planned and actual spending.
6. Easy understanding of the savings-reserve effect.
7. Useful historical information without overwhelming the user.
8. Complete offline functionality and strong privacy by default.
9. Optional multi-device sync that never compromises local-first behavior.
10. Optional Shared Expenses between trusted users that derive from, rather than
    duplicate, personal records.
11. Minimal unnecessary complexity.

The user should be able to open the application and understand the current financial
situation within a few seconds.
