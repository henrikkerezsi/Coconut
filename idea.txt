# Coconut — Budget Tracking Application

## 1. Purpose

Coconut is a private, offline-first Android budget management application designed around
a monthly spending allowance and a savings reserve.

The application is intended for a single user and models the user's personal financial
system. It is not a general-purpose banking or accounting application.

Optionally, two or more authenticated Coconut users can connect in a Shared Space to
track shared expenses (typically a couple). A Shared Space extends, and never replaces,
each user's personal financial system.

There is no bank integration, advertising, analytics, or any required
internet connection. All financial data is stored locally on the device in a SQLite
database that is the single source of truth.

The application is fully usable offline. An optional, opt-in sync to a user-owned
Supabase project can mirror the local database so it is available on the user's own
multiple devices. Sync is never required to use the application and never replaces the
local database as the source of truth.

---

## 2. Core Financial Model

The application is organized around independent monthly accounting periods.

Each month has:
- A guaranteed monthly allowance.
- Fixed expenses.
- Estimated/variable fixed expenses.
- Flexible spending budgets.
- Actual transactions.
- A calculated total monthly spending.
- A calculated difference between actual spending and the monthly allowance.
- A starting and ending savings-reserve value.

The monthly allowance represents the amount of money reliably available for ordinary
monthly spending. It is not a conventional spending budget and does not impose an
artificial spending limit.

The user's planned spending may therefore be greater than the monthly allowance.
The application shows this clearly rather than treating it as an error.

## 3. Savings Reserve

The application maintains a separate savings-reserve balance.

The reserve is not treated as an ordinary spending account and does not contain individual
bank transactions. It represents accumulated money available to compensate for months
where spending exceeds the allowance, as well as accumulated savings from months where
spending is below the allowance.

At the end of each month:

    actual monthly spending - monthly allowance = reserve adjustment

The reserve is reduced when actual spending exceeds the allowance and increased when
actual spending is below the allowance.

The resulting reserve balance carries forward into subsequent months.

There is no manual transfer between the reserve and the current month. The adjustment
above is the only movement between the two, and it is applied by the app when the month
is closed. Each closing records the movement it applied as a permanent entry in the
reserve history, so that the movement can be audited per month. The reserve history
lists every one of these movements, newest first, showing for each closed month whether
the adjustment added to the reserve or drew from it.

Closing a month is final. A closed month cannot be reopened or edited; corrections are
made by editing the current month before closing it.

### 3.0 Which month the app is on

The month changes when a month is closed, and at no other time. The calendar moving on
does not move the app on.

The period shown is therefore the oldest month that is still open. Closing a month
immediately starts the next period, so closing September moves the app to October even
while it is still technically September. The other way round, on the 1st of October a
September that has not been closed yet keeps the app on September, because that month
is still the one being worked on.

When every month is closed, the period after the latest one becomes the active period
and is created, carrying the reserve balance the last closed month ended on. A period
that has already gone by is never created, so a month the user skipped entirely is not
filled in with invented history.

### 3.0.1 What can be dated

Only the active month accepts new records, and a record can only carry a date inside
that month: from its first day to its last. Nothing can be backdated into a month that
has been closed, and nothing can be dated ahead into a month that has not been worked on.

Because the active period follows closing and not the calendar, this has a visible
consequence. Closing September on the 30th moves the app to October, so on that 30th the
only dates that can be recorded are October dates. The other way round, on the 1st of
October an unclosed September keeps September active, so only September dates can be
recorded and the picker will not even offer an October one.

A record that already belongs to a closed month is shown as it was and can no longer be
edited, since a closed month is final.

### 3.1 The closing window

A month can be closed from 36 hours before it ends until 24 hours after it ended, a
window of 60 hours. For a month that ends at midnight, the window therefore opens at
noon, one and a half days before the last day, and closes at midnight at the end of the
1st of the following month. Because the window reaches into the following month, a month
can still be closed on the 1st.

While the window is open, the overview shows a prompt that the month is coming to an end
and offers to close it. The prompt is shown on the overview screen only.

Once the window has passed, the application closes the month itself. Any purchase the
user did not judge is recorded as neutral, so a month is never left open and unsettled
and the reserve balance of the following month is never carried from a stale figure.

### 3.2 Closing a month

Closing a month is a review of that month, presented on one screen:

- How much was spent in total, and how much of that went to fixed expenses and to
  subscriptions.
- How much each budget received.
- Every transaction of the month, each with a three-stop judgement of how much value the
  purchase turned out to be: regret, neutral, or good. A purchase that is not judged is
  neutral, and this is the whole purpose of the review, so the user can look back and see
  how usefully they spent their money. The judgements are kept for later statistics.
- A purchase that is derived from a shared expense is judged like any other. The
  judgement is kept on the user's own copy of the purchase and survives a later change
  to the shared expense.

The final action is closing the month, which first asks for confirmation and states that
it is final and cannot be undone. Confirming closes the month, records the reserve
movement, and presents the closing report of that month.

### 3.3 Starting a month

A month only ever comes into existence because the user started it. The application never
creates a period on its own, so both a new user and a user who has just closed a month
are asked the same question: what does the coming month look like?

Starting a month is presented on one screen, and it is what the main interface waits for.
The overview and the other month-based screens are behind it until the month exists,
because they are built around a month. Settings and the planning screens stay reachable
throughout, so the user can go and set up what the screen is missing.

The screen shows, before anything is written:

- The savings reserve the month starts on, carried forward from the month before it.
- The monthly allowance.
- The average monthly spending so far, or that there is no history yet.
- What the month has to spend, being the allowance plus any planned draw.
- The fixed expenses of the month at their expected amounts, and its subscription
  charges. These are deducted before anything is planned, because they are not the user's
  choice.
- What is therefore left to spread across the budgets.

The user may state how much they intend to draw from the reserve for that month. This is a
planning figure only. It moves no money, is not part of the month's accounting, and leaves
the reserve balance and its history untouched; the real movement is decided at the end of
the month by the closing rule, which may well be no movement at all. A draw can never be
more than the reserve holds. It is offered because it is what makes the plan below it
meaningful: it raises what the month has to spend for planning purposes only. The figure
becomes the draw the month starts planning with, and is recorded as such (§3.4).

The figure is signed, because the two intentions are opposites. A positive amount is money
the user intends to take out of the reserve and spend, which raises what the month has to
plan. A negative amount is money the user intends to set aside on top of what the month
already leaves over, and the plan is then sized around what is left, so that the saving is
not quietly spent. A negative amount is not limited by the reserve: setting money aside
only ever adds to it. The user may also have no intention either way, which is a draw of
zero.

The remaining amount is then planned across the budgets, each of which starts from its
default amount. A budget cannot be planned above what the month actually has available
once the fixed expenses, the subscriptions and the other budgets are paid for, and the
month cannot be started while the plan as a whole exceeds what it has. Nothing is required:
a user with no allowance, no fixed expenses, no subscriptions or no budgets can still start
the month, and the screen links to the setting, the fixed expenses, the subscriptions and
the budgets so nothing is a dead end.

Starting the month writes it, its expected fixed expenses, its subscription charges and
the plan in a single step, so a month never exists half-planned. From then on the main
interface is reachable again.

### 3.4 Re-planning a month

A month is planned once and then re-planned as often as the user needs, in one place and
as one explicit action. The plan of a running month is the month's own, not a draft, so
leaving the screen without saving changes nothing.

Re-planning is reached from Settings, under Planning, as "This month's plan", and from
Flexible Budgets. It shows the same figures as starting a month does, but read from the
month itself rather than from the current settings: the month's own allowance, the fixed
expenses and subscription charges it was materialized with, the amounts its budgets
already stand at, and the draw it already plans with. A month is never quietly
re-estimated by being re-planned.

Saving records what changed, which is the reason it is one action rather than several
edits. For every budget whose amount moved, the amount it was at and the amount it is
now are recorded. A change to the draw is recorded with the amount it was at and the
amount it is now, together with the budget the extra was handed to where one budget
absorbed exactly the difference. The amounts a month is currently planned at are
recalculated from these changes, so the month always stands at the plan the user last
committed to.

The record of a month that was planned before it existed opens with the first re-plan,
at the amounts the month stood at that moment, and makes no claim about how it came to
be there. A month is never re-planned into a plan that exceeds what it has available,
and the draw is still bounded by the reserve it starts on.

The planned draw exists to size the plan. It is not part of the month's accounting, so
the overview, the forecast and the closing rule are unchanged by it: they work from the
month's bare allowance. A re-plan that raises the draw and allocates the extra therefore
shows on the overview as spending that the month has not accounted for, which is true
and is left visible rather than reconciled away.

## 4. Fixed Expenses

Users define recurring fixed expenses that automatically belong to each relevant month.

Each fixed expense has:
- Name.
- Expected amount.
- Recurrence/configuration.
- Whether the amount is genuinely fixed or estimated/variable.
- Current month's actual amount where applicable.

Genuinely fixed expenses are automatically accounted for using their defined amount.

Variable fixed expenses have an expected amount used for monthly planning. The expected
amount can be determined manually or derived from historical actual amounts.

Supported estimation strategies:
- Manually specified amount.
- Previous month's actual amount.
- Average of a configurable number of previous months.
- Historical average.

When the actual bill becomes known, the user replaces/corrects the month's expected
amount with the actual amount without creating a second expense.

The application retains the distinction between expected and actual values so that
historical statistics and future estimates use actual spending.

---

## 5. Flexible Spending Budgets

Users define discretionary spending categories with monthly budget amounts.

Budgets represent intended spending allocations, not hard restrictions.

A budget is a definition: what the category is for, and what it is planned to cost by
default. The amount a particular month stands at is not part of the definition and is
not changed from here. Setting the month's amounts is one explicit action in planning
(§3.4), which also records what changed; the screen therefore offers "Plan this month"
rather than a list of the current month's amounts to edit one at a time.

The sum of flexible budgets and fixed expenses may exceed the monthly allowance. This is
intentional and supported naturally.

For each budget:
- Planned amount.
- Actual amount spent.
- Remaining amount.
- Difference between planned and actual spending.

Budgets are independently configurable and support being changed for individual months
without unnecessarily changing historical months.

---

## 6. Transactions

Actual discretionary spending is recorded as individual transactions.

A transaction contains:
- Unique identifier.
- Date.
- Amount.
- Category/budget.
- Merchant or description.
- Optional note.

Transactions are manually entered by the user. A transaction can only be dated inside
the active month (see §3.0.1), so the date picker offers no other days.

Transactions may also originate from a shared expense: each participant gets exactly one
linked personal transaction whose amount equals that participant's split. Linked
transactions are derived from the shared expense and are never edited as a separate
record.

Entering a transaction assigned to a budget immediately updates the relevant budget's
actual spending and the month's overall actual spending.

Transaction entry is extremely fast and simple — this is a frequent operation.

The system remembers previous merchant/category associations locally and suggests
categories during future transaction entry. Suggestions remain editable and do not
prevent choosing another category.

---

## 7. Monthly Accounting

Each month distinguishes clearly between:
- Allowance.
- Planned spending.
- Actual spending.
- Remaining allowance.
- Expected month-end spending.
- Expected reserve adjustment.
- Final reserve adjustment once the month is closed.

The current month is the primary focus of the application.

Previous months remain accessible for review and statistics but do not clutter the normal
current-month interface.

Months are independently preserved so that modifying a current configuration does not
unexpectedly rewrite historical financial records.

---

## 8. Forecasting

The application distinguishes actual financial results from planning/forecasting.

Visible information:
- How much has actually been spent so far.
- How much remains in each budget.
- What fixed expenses are expected.
- What total spending is currently planned or forecast.
- What reserve adjustment is currently expected.

Forecasts are clearly presented as estimates and must not be confused with actual
recorded spending.

## 9. Main Screens

### Overview
Primary screen for the current month. Shows:
- Monthly allowance.
- Actual total spending.
- Remaining allowance.
- Fixed-expense status.
- Flexible-budget status.
- Current savings reserve.
- Current or projected reserve adjustment.
- Important deviations between expected and actual spending.

Prioritizes clarity over displaying every available piece of information.

### Transactions
Chronological list of actual transactions.
- Adding, editing, deleting transactions.
- Viewing transaction details.
- Filtering/searching.
- Identifying the associated budget/category.

### Statistics
Historical financial information and trends:
- Monthly spending history.
- Average monthly spending.
- Budget usage (spend vs. its monthly plan, averaged).
- Fixed-expense history.
- Savings-reserve development.
- Savings trend (monthly amount added to or drawn from the reserve).
- Historical differences between allowance and actual spending.

Focused on useful personal budgeting information, not comprehensive financial analytics.

### Shared
Bottom-bar tab for Shared Spaces:
- Space members and the open Shared Period (start date — now), with only that period's
  expenses listed like transactions.
- A prominent "Close Period" action that generates the closing report (who paid, each
  share, each member's paid total, net who-owes-whom). Accepted: period closed and
  immutable, report stored; cancelled: period stays open.
- Read-only access to all past closing reports.

### This month's plan
Re-planning the running month: its budgets, its draw from the reserve, and the record of
what each change was. Reached from Settings and from Flexible Budgets. See §3.4.

### Settings / Planning
Configuration for:
- Monthly allowance.
- Savings reserve.
- This month's plan (re-planning, §3.4).
- Fixed expenses.
- Variable fixed-expense estimation methods.
- Flexible budgets.
- Categories.
- Cloud sync (Supabase).
- Data backup and restoration.
- Application preferences.

Previous months remain accessible.

A historical month preserves:
- Allowance.
- Fixed-expense expectations and actuals.
- Budget definitions and amounts.
- Transactions.
- Actual spending.

## 11. Data Storage and Cloud Sync

### 11.1 Local database as source of truth

All reads and writes go to a local SQLite database on the device. The local database is
always the source of truth. The application never loads financial data from the cloud.

The database separates persistent configuration from month-specific financial records.

Capabilities:
- Query current-month data.
- Retrieve historical months.
- Calculate budget totals.
- Calculate monthly totals.
- Calculate historical averages.
- Update variable-expense estimates.
- Recalculate reserve changes deterministically.

Financial calculations are implemented as separate business logic, not embedded in UI
components.

### 11.2 Optional synchronization to Supabase

The user may enable optional synchronization to their own Supabase project so the same
personal dataset is available across their own devices.

- Sync is opt-in. Without it the application is completely local and makes no network
  requests.
- The local database is always written first, then a background, best-effort sync pushes
  the changes to Supabase when the network is available. Sync never blocks normal use and
  never fails local operations.
- Other devices pull those changes into their own local SQLite database; the app on every
  device continues to read and write locally only.
- Sync mirrors row-level changes, not the whole database on every write. Each synced row
  carries a stable UUID and a timestamp and follows last-write-wins conflict resolution.
- The Supabase project is owned by the user and used only for this mirror. No third party,
  tracking, or analytics is involved.

### 11.3 Sync lifecycle

- A write to a local table records the change in a local sync outbox and tombstone log.
- A sync run pushes the recorded upserts and tombstones to Supabase and pulls any changes
  made by the user's other devices.
- Conflicts between devices are resolved by last-write-wins using each row's update
  timestamp.
- Sync state (last push position, last pull time, connection status) is stored locally and
  displayed in Settings.

## 12. Shared Expenses

### 12.1 Concept

Each user keeps an independent Coconut account and personal financial system. A Shared
Space connects two or more authenticated Coconut users (typically a couple) and holds
shared expenses, their splits, and period-closing reports.

An expense belongs to a **Shared Period**. A period opens when the space starts or the
previous period closes, and stays open until it is settled. Members record expenses in the
current open period; closing a period settles it permanently and immediately opens the
next one.

The shared-expense relationship is authoritative:

    Shared Expense
      ├── total amount
      ├── payer (a member)
      └── per-participant split
             ├── participant A's personal linked transaction
             └── participant B's personal linked transaction

A participant's personal transaction amount is always derived from their split. Editing a
shared expense re-derives the linked personal transactions; the split is never maintained
independently in two places.

### 12.2 Authentication and security

One Coconut Supabase project hosts all users. There are no per-user Supabase projects,
and users do not share one Supabase Auth account; each Coconut user is a separate
Supabase Auth user.

Supabase Row Level Security distinguishes personal rows from shared rows:

- Personal rows: `user_id = auth.uid()`.
- Shared rows: `auth.uid()` is a member of the relevant Shared Space.

A user cannot read or write another user's personal rows, join a space arbitrarily, or
create expenses/splits for users outside the space. Every new exposed table has RLS
enabled, and member vs. non-member RLS behavior is tested.

### 12.3 Database model

Adapted with additive, incremental migrations only; existing personal data stays intact.
Shared balances are derived from explicit states, never stored as mutable amounts.

- `shared_spaces` — name, creator, timestamps, deleted flag.
- `shared_space_members` — space, user, role (`owner`/`member`), joined; unique
  `(space_id, user_id)`.
- `shared_periods` — space, start date, end date (null while open), status
  (`open`/`closed`), timestamps. Contiguous: the next period starts where the previous
  one closed.
- `shared_expenses` — period, description, total amount, date, paid by (a member of that
  period), note, creator, timestamps, deleted flag. Every expense belongs to exactly one
  period, normally the space's current open period.
- `shared_expense_splits` — expense, user, explicit monetary share in cents. Only
  explicit amounts are persisted; 50/50 and percentage splits are UI conveniences that
  resolve to amounts. Sum of splits equals the total.
- `shared_period_reports` — permanent closing reports. A generated report is a snapshot:
  the period's expenses (description, date, total, payer, each participant's share), each
  member's total paid, and the net who-owes-whom settlement. Reports are stored
  permanently and are immutable once accepted.

Settlements are the net obligations recorded by an accepted closing report; there are no
standalone settlement rows and no ad-hoc mid-period settlement.

Enforced invariants: totals positive; splits non-negative and summing to the total; payer
and split users are space members; every member has a split for every period expense; an
expense's period is the space's current open period; closed periods are never edited.
Validated at data-application and database/business-logic level, never UI-only.

### 12.4 Personal transaction provenance

The existing personal transaction model is extended, not duplicated, with a provenance
reference (`origin_type` / `origin_id`). Manually entered transactions use `manual`; a
transaction created from a shared expense references that expense's UUID. The
transaction's own stable ID remains unchanged.

Each member's client derives its own linked personal transaction locally from the shared
expense and that member's split in the shared table; this personal amount is never synced
as a separate authoritative record. When splits change, linked transactions update in
place (never duplicated); when a shared expense is deleted, linked transactions follow the
app's deletion/tombstone model — no orphaned transactions.

### 12.5 Period closing and balances

The current balance is derived only from the open period's expenses and splits (closed
periods are settled and frozen), with a clear sign convention and reduced to a single net
"who owes whom" amount between each pair of members.

Closing: a member clicks **Close Period**. Coconut generates a Shared Period Closing
Report automatically:

- Every expense in the period: description, date, who paid, the amount, and each
  participant's share.
- Each member's total amount paid.
- The net "who owes whom how much" settlement.

The member accepts or cancels the report. Accepted: the period is closed, its expenses
become immutable, the report is stored permanently, and the next period opens. Cancelled:
the report is discarded and the period stays open. Old reports remain accessible and
read-only.

### 12.6 Shared Space lifecycle

- Create: one user creates the space.
- Invite/join: additional users join only through an explicit, secure invitation
  (invitation token/deep link or pending membership). Knowing a space UUID alone grants
  nothing.
- Leave/remove: a member can be removed or leave without deleting historical expenses or
  reports.

### 12.7 Sync integration

Shared data (spaces, members, periods, expenses, splits, reports) uses the same local-first
sync engine as personal data: stable UUIDs, timestamps, outbox/tombstone logs, and the
existing last-write-wins conflict strategy. Multiple members' devices pull the same shared
rows. Splits are validated after synchronization so total != sum of splits is never
silently introduced; a report may only be accepted once all synchronized data is
consistent.

### 12.8 UI

A dedicated **Shared** tab on the bottom bar shows the space, its members, the open period
header (start date — now), and only the current period's expenses, listed like
transactions. A prominent **Close Period** button at the bottom opens the closing report
with accept/cancel. Past closing reports are accessible and read-only. Adding an expense
is fast: description, amount, date, paid by (me / another member), split method, optional
note. Personal transaction views visibly identify shared-linked transactions and navigate
to the originating shared expense.

No separate category system: a shared expense may carry an optional category/merchant
association, and the resulting personal transaction uses each participant's own budget
category.

### 12.9 Non-goals

No real-time collaborative editing, no new backend, no second database, no separate
Supabase projects, no dedicated global state for this feature, no bank integration, no
general Splitwise replacement, and no ad-hoc mid-period settlements — money is settled only
when a period closes. Use the existing Coconut architecture throughout.

## 13. Backup and Restore

Synchronization and backup are separate features.

- Export complete application data to a portable file (the full SQLite database).
- Import to restore all data.
- Backup includes all information required to reconstruct financial history and
  configuration.
- Backup works entirely on-device; no cloud service is required for it.

---

## 14. Privacy

- Works completely offline.
- Stores financial information locally.
- No network requests during normal, non-synced operation.
- No analytics or tracking. No account in local-only mode; Supabase Auth accounts exist
  only when the user opts into multi-device sync and Shared Expenses.
- No advertising.
- No bank credentials or banking integration.
- Avoids unnecessary permissions.

Financial information leaves the device only when the user explicitly enables
synchronization to their own Supabase project; the app never sends data anywhere else.

## 15. Technical Stack

- React Native (via Expo)
- Expo SDK
- TypeScript (strict mode)
- expo-sqlite (local SQLite database)
- Expo Router (navigation)
- React Native Paper (Material Design 3 UI components)
- dayjs (date handling)
- Jest + jest-expo (unit testing)
- @supabase/supabase-js (optional cloud sync mirror only)
- Expo Web / react-native-web (desktop web builds)

Architecture:
- Business logic, database access, sync, and UI have clear separation.
- Supabase is the only permitted backend: an optional sync mirror for the user's own
  data and the host for Shared Expenses. Supabase Auth identifies users only for these
  optional features; Row Level Security separates personal and shared rows. No other
  backend, provider, or analytics is used.
- Small dependency footprint.
- Favor Expo-supported functionality.
- The application must build and run as a local desktop web application and remain
  structured so a future native desktop app can reuse the same code with minimal work.

---

## 16. Desktop and Web

Coconut targets Android first, but the code must also compile as a desktop web
application that runs locally.

- The web build is a standard Expo Web (react-native-web) single-page build that can be
  served and opened locally.
- expo-sqlite supports web via a WebAssembly SQLite build, so the same database layer and
  the same sync logic run on desktop web without platform-specific forks.
- Native-only capabilities (file sharing, native date pickers) are isolated behind
  platform-safe wrappers so the web build always compiles and degrades gracefully.
- The UI and services layers must stay platform-agnostic. Keeping the database, sync, and
  services layers free of platform bindings is what makes a future desktop app simple: the
  same modules can be packaged with the desktop runtime of choice.

---

## 17. Design Philosophy

Focused personal tool, not a commercial banking application.

Priorities:
1. Extremely clear current-month overview.
2. Fast manual transaction entry.
3. Accurate and predictable calculations.
4. Simple handling of recurring and variable fixed expenses.
5. Clear separation between planned and actual spending.
6. Easy understanding of the savings-reserve effect.
7. Useful historical information without overwhelming the user.
8. Complete offline functionality and strong privacy by default.
9. Optional multi-device sync that never compromises local-first behavior.
10. Optional Shared Expenses between trusted users that derive from, rather than
    duplicate, personal records.
11. Minimal unnecessary complexity.

The user should be able to open the application and understand the current financial
situation within a few seconds.
